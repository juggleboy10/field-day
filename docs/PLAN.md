# Field Day: the plan for the four overhauls

This answers `docs/OVERHAULS.md`. It was written after reading the code, measuring it (`tools/measure.py`) and trying
the riskiest idea in a throwaway build. Each numbered step is small enough to do, test and release on its own.

**Order:** 1 (load on demand) → 4a (measure and the cheap graphics wins) → 2+3 together (the match kit) → 4b (the
heavy places). 4 is split because its first half is cheap and independent, and its second half is easier once places
load one at a time.

## Overhaul 1: load each place when you go there

### The design: plain scripts that share the page's scope

Today everything sits inside one wrapper function, which is why every file can see every other file's names. The
least disruptive way to split it: **remove the wrapper and make each file an ordinary script**. Top-level `const`,
`let` and `function` in ordinary scripts are shared by every script on the page, including ones added later. So a
game file loaded on demand sees `V3`, `newLevel`, `CAMERA` and the rest exactly as it does now, with live values and
**no changes inside the game files**.

I tried it: the whole game, built as 99 separate scripts with the 75 game files as external files, runs with all 61
places after changing two lines (two top-level `return`s in `core/setup.js`, which need to become a flag or a throw).
Starting with only the clubhouse and adding a game's script later also works in principle; what breaks is listed in
step 1.3.

Why not real modules (`import`/`export`): every one of the 36,000 lines uses shared names implicitly. Converting means
touching every file and writing about 350 exports and thousands of imports, for no gain a player would notice.

**The one real risk:** names at the top level become page globals. Function names can collide with browser built-ins,
and the Claude page's own script might declare a `const` with one of our names, which would stop our script from
loading at all. Step 1.1 tests exactly this before anything else is built on it. Fallback if it fails on the Claude
page: keep the wrapper for the core, and have the build wrap each game as `defineLevel(function (S) { const { V3,
newLevel, … } = S; … })`, with the list of names generated by the build from a parser (acorn). That costs a build
tool and loses live `let` bindings (only a handful of core `let`s exist), but nothing else.

### Steps

**Where this stands (v101):** 1.0 to 1.3 are done, and 1.4 in a simple form: places stay inside the one `index.html` as
text and are run on first visit (startup script time about 3 s to 0.4 s on the test machine). Still to do from 1.4: a
fade and a VR "Loading" card, and warming up likely places. 1.5 (separate files) is now optional: it would cut the
download, not the startup time.

**1.0 Guard rails (no behaviour change).**
- Replace `build.sh` with `tools/build.py` (same output for now), so later steps can emit several files.
- Add `tools/check_scope.py`, which fails the build on:
  - a top-level name declared twice
  - a top-level name that collides with a `window` property (checked in the headless browser against a blank page)
  - a top-level `return`
- Release as is.

**1.1 Remove the wrapper, still one file.**
- Emit the core as one inline `<script>` starting `'use strict';`, and each game as its own inline `<script>`.
- An error in one script no longer stops the ones after it, so add a `window.__fdFailed` flag that later scripts and
  the start screen check.
- Test: full suite, then **the owner tries it on the Quest and on the Claude page**. This is the go/no-go for the
  design. If the Claude page fails, switch to the fallback above before going further.

**1.2 Untangle the few real cross-file links.** Found by analysis; the rest of the apparent links are just words in
strings.
- `drawRows` lives in `games/hoops.js` and 35 games use it: move it to `core/shared.js`.
- `app/main.js` sets `hoops.throwSpeed`, `baseball.throwSpeed`, `baseball.lockWhileHolding`, `discgolf.walkSpeed` by
  name at startup: move each into its own game file. The "can hop" list becomes a flag in `LEVEL_META`.
- Shared libraries become **packs** that load before the games that need them:
  - quests: `quest-shared.js`, `quest-engine.js` (dungeon, frostpeak, hexwood, pirate cove, siege)
  - study: `study.js`, `study-content.js`, `triggers-content.js` (the six study games)
  - carnival: `carnival.js` (duck shoot, light speed, ring toss, strongman, whack)
  - trivia questions: `trivia-questions.js` (trivia)
- Other files use the words `scatter` and `ring` (helpers in `quest-shared.js`) only as their own local names, so
  those stay in the quest pack. `check_scope.py` (with a real parser) confirms this kind of thing from here on.
- Write `src/manifest.json`: for each place, its files in load order (packs first). `check_scope.py` then also fails
  if a game uses a name from a file that isn't in its own list.

**1.3 Make the core work when a place isn't built.** Add a `?eager` switch that loads everything at startup, so the 53
existing tests keep passing unchanged while this is done. Places that assume every level exists:
- `app/net.js` lines 57 and 148 and `goSolo` (loops over `LEVELS`; crashes on a gap)
- `core/records.js` lines 136–140 (walks all levels for `recDefs`): move each game's record names into `LEVEL_META` as
  plain data, since the clubhouse boards list every game
- `app/main.js` line 40 (overlay loop), `app/modes.js` `switchLevel`, `app/menu.js` tiles
- `app/camera.js` placed prints (`LEVELS[o.lv].buttons`): attach a print's button when its level loads
- music themes that games register on load: fine, they arrive with the game
- Not a problem: `readPresence` is only called for friends in the place you're in (`net.js` line 98).

**1.4 The loader.**
- `loadLevel(i)` returns a promise: adds the script tags from the manifest in order, and resolves when `LEVELS[i]`
  exists.
- `switchLevel` becomes: fade out, show "Loading Birdwatching Trail…" (in VR, on a card in front of you), load, build,
  fade in.
- If a file fails: say so, stay where you are, offer to retry.
- Warm up in the background: the place whose portal you're walking toward, and the three you play most (from prefs).
- Tests: `window.__fd.load(i)` for tests to wait on; switch the suite from `?eager` to waiting, a few files at a time.

**1.5 Files with the version in their names, and no more stale copies.**
- The build writes `levels/<name>.<hash>.js`, and `index.html` carries the manifest. An old page can never pull a new
  file or the other way round.
- Hostinger: ship `.htaccess` that makes `index.html` always re-check and lets `levels/` cache forever. This removes the
  `?v=` workaround. The upload becomes a folder; each release lists which files changed.
- Claude page: publish `index.html` plus the level files as supporting files (the publish tool takes a file map;
  scripts load by relative path).
- Keep `tools/build.py --single` (today's one-file build) as the rollback and for quick local tests.

**1.6 (Later, optional) letting go of places you've left.** Keep the last three built; dispose of the rest.
Rebuilding needs each game to be a function that can run again, so `const hoops = (() => {` becomes
`defineLevel(0, () => {`. It's a mechanical change to 60 files; only worth it if Quest memory turns out to be a
problem after 1.4.

**Result to expect:** first load 513 KB (core plus clubhouse) in place of 2.82 MB, and startup script time roughly a
tenth of today's. Each place costs its own 20 to 120 ms (desktop) the first time you enter it.

**Traps.**
- Game files run later than they used to, after `main.js`. Anything a game did at load that the core read during
  startup must move (steps 1.2 and 1.3 cover the ones found).
- A friend can be in a place you haven't loaded: only their `lv` number is needed for "who's where", and that is
  already in the core.
- Two scripts can't both declare the same top-level name. That's already true today; `check_scope.py` keeps it true.

## Overhauls 2 and 3: one match kit (multiplayer and the shared game machinery together)

These are one design. A game declares its seats, phases and rules; the kit runs the lobby, the countdown, the referee,
the messages and the scoreboard.

### What exists to build on
- `core/claims.js`: balls and bats belong to whoever touched them last, with a tie-break every page agrees on, and are
  adopted by the lowest peer when someone leaves. This stays as the "owned objects" tier.
- 17 games pick a referee as "lowest peer id here", each with its own copy of the code (`isHost` appears 159 times).
- `games/brawl.js` is already shaped the right way: a pure `step(fighter, input, dt)`, inputs as press counters,
  the referee's snapshot in presence, friends asking the referee to start. **The kit is extracted from Brawl.**

### The layers

**Transport (`core/net`).** Keep presence for heads, hands and small state. Add a match channel with one interface,
`MATCH.send(obj)` / `MATCH.on(fn)`, and two carriers:
- Own website: a trystero action (direct, in order, no 4 KiB limit; the photo wall already uses one).
- Claude page: either a sub-room (`room.join('m-' + levelId)`, which gives the referee a second 4 KiB presence) or an
  event topic opened to players (`room: { topics: { m: 'interact' } }`, a permissions change the owner must approve).
  **Step 2.0 measures both** (delivery rate, delay, drops) with a probe page before choosing. Events can drop, which is
  fine for snapshots (each is the whole state) and for inputs sent as counters.

**The referee.** One rule in the core, replacing the 17 copies:
- The referee is the lowest peer id among seated players **whose page is alive**. Every page puts a heartbeat counter
  in presence; a page silent for 1.5 s is skipped.
- A page that knows it's going away says so: on `visibilitychange` (tab hidden, headset taken off, the frame loop
  stops) it sets an "away" flag so hand-over is immediate. Today a referee who takes their headset off freezes the
  game for everyone.
- Hand-over: every page keeps the latest snapshot. The new referee continues from it and raises an `epoch` number;
  pages ignore anything from an older epoch. So everything the referee needs (timers, bot plans, the bomb clock) must
  be in the snapshot or cheap to re-derive.

**Inputs.** Stick positions (rounded) plus a counter per button, as Brawl does. The referee's snapshot says the last
counter it used from each player.

**Showing it.**
- Your own character: the game's `step` runs on your page immediately; when a snapshot arrives, start from it and
  re-apply the inputs the referee hasn't used yet, then ease out any small difference over 100 ms. Opt-in per game;
  needs a pure `step`.
- Everyone else: draw 100 ms in the past, between the two nearest snapshots. Snapshots carry the referee's clock;
  never compare clocks between pages.

**Snapshots.** Whole state, rounded integers, 15 to 20 a second. Four fighters and eight shots is about 400 bytes.

**Three tiers, chosen per game:**
- *Personal*: solo booths and lanes; only your scoreboard row is shared.
- *Owned objects*: `claims.js` as now (catch, hoops, bowling balls), plus the alive-page rule for adoption.
- *Referee*: Brawl, dodgeball, capture the flag, musical chairs, cornhole turns, gorilla tag, haunted, and the rest of
  the 17.

### The kit a game uses (overhaul 3)

```js
MATCH.define(L, {
  seats: { min: 2, max: 4, bots: true, teams: 0 },
  phases: { count: 3, over: 5 },                 // lobby -> count -> play -> over -> lobby
  setup(m) { … },                                // place everyone
  step(m, inputs, dt) { … },                     // the rules; runs on the referee (and for prediction)
  snapshot(m) { … }, apply(m, snap) { … },
  row(seat) { … }, records: ['wins', 'kos'],
});
```

The kit provides:
- people first, bots filling the rest
- a Start button and HUD action; "ask the referee to start"
- the countdown and winner banners
- joining mid-match (you watch until the next round)
- End game, bot difficulty and records wired in
- scoreboard rows; the "who's the referee" indicator

### Steps

**Where this stands (v107):** 2.0 and 2.1 are done.
- Carrier: match messages stay in presence for now (Brawl's snapshot already fits, at 20 a second); no permissions
  change and no probe needed. A separate channel can come in behind the same interface later if a game needs more.
- `FAKE_ROOM` takes `?lag=`, `&jitter=`, `&drop=`, and `__netStop()` / `__netGo()` for a page that goes silent.
- `core/referee.js`: heartbeat, away flag, a sticky referee and hand-over numbers (see the comments there).
  `playersHere(L)`, `refereeOf(L)`, `amReferee(L)`; `L.refPool` for games where only some players may referee.
  About 30 games use it in place of their own copies. `tests/v107.py` checks the hand-overs under 120 ms of delay.
- 2.2 (v108): `core/match.js` (`MATCH.define`: seats, lifecycle, start requests, the phase in presence); Brawl uses it.
- 2.3 and 2.4 for Brawl (v109): `MATCH.timeline` draws other fighters 100 ms behind, between snapshots stamped with the
  referee's clock; your own fighter's movement is predicted (`PRED` turns off hits, shots, KOs and sounds while
  predicting) and reconciled from the referee's acks (`ba`, against `bi[10]`). `tests/v109.py`.
- v110: dodgeball and snowball draw their bots from the timeline, and a new referee carries on the round clock.
  `MATCH.timeline` adapts how far behind it draws (100 to 400 ms) to how unevenly snapshots arrive, easing changes.
  Your own movement in those games is already your own page's, as are your hits: nothing to predict there.
- v111: pickleball already hands the ball to whoever it's heading for (own hits never lag); its court now counts only
  live players, so a frozen player's spot goes to the bot and the ball moves on.
- v114: musical chairs times each player from when their own music stopped (fair on a slow connection).
- From v115 the owner asked to leave the referee and hand-over work there and move on to the game kit (overhaul 3).
- v115: `VR_TOAST` (core/shared.js): every `showToast` also shows on a panel in front of you in the headset (the HTML
  toast never showed in VR). v116: `ANNOUNCE.count / go / win`, the same big countdown, GO and result (with sounds) on
  screen and in the headset; `MATCH.define` calls it itself (`result`, `goText`, `announce: false`). About 20 games use
  it: Brawl, dodgeball, snowball, the five races, chairs, cornhole, pickleball, laser tag, soccer, paintball, CTF, hot
  potato, trivia, bowling, darts, hoops, charades, boxing, football.
- v117 (frame rate, 4b again): hoops 271 → 28 draws (each skyline building one material, then merged), duck shoot
  244 → 82 (each duck merged within itself; the fairground merged; the Ferris wheel's turning parts merged within the
  wheel, which helps every carnival place), football 244 → 101 (each player merged within itself, legs left out).
  `tests/v117.py [place ...]`.
- Not yet: games don't all keep everything a new referee needs in their shared state (timers, bot plans). Each game's
  move onto the kit (2.5) checks that with a referee hand-over in its two-page test.

**2.0** Probe the Claude page's sub-rooms and events; choose the carrier. Extend `FAKE_ROOM` in the tests with delay,
jitter, drops and "this page stops", so every later step is tested under 120 ms of delay.
**2.1** The referee rule and heartbeat in the core; replace the copies in the 17 games one at a time (behaviour stays
the same apart from surviving a referee who goes away). Each has a two-page test already or gets one.
**2.2** `MATCH` lifecycle and seats, extracted from Brawl; Brawl moves onto it. Its test (`tests/v98.py`) must pass
unchanged.
**2.3** The match channel, snapshots at a steady rate, drawing others 100 ms behind. Brawl and dodgeball.
**2.4** Prediction for your own character. Brawl first (it has the pure `step`), then pickleball doubles.
**2.5** Move games over a few per release, in this order: versus games with a referee, team games, turn-taking games,
then solo games (which only use the lifecycle and records parts). Quests, charades and birdwatching use parts only.

**Done when:** as the brief says, plus: unplugging the referee mid-match in the two-page test leaves the other page
playing within 2 seconds, at the same score.

**Traps.**
- Peer ids are different kinds of thing on the Claude page and on the own-website transport; only ever compare ids from
  the same room.
- Presence keys you stop sending must be nulled (the core does this); the match channel has no such memory, so every
  snapshot must be complete.
- The frame loop stops when a tab is hidden. A referee must never rely on frames for time: use the clock, and give up
  the role when hidden.
- Don't predict things the player doesn't control (being hit, bombs); only their own movement.

## Overhaul 4: frame rate on Quest 2

### 4a: measure and the cheap wins (do right after overhaul 1)

**Where this stands (v102):** done. `tools/measure.py` measures through the loader (first-visit build time and draw
cost per place); `tests/budgets.json` holds each place to today's numbers (`tests/budgets.py`), 24 places are over 150
calls; the watch has a frame-rate readout (Settings); VR uses full fixed foveation and a sharpness setting; the eyepiece
draws every other frame in a place over 150 calls. Waiting on: the owner's readings from a Quest 2.

- `tools/measure.py` is in the repo and gives the ranking above. Add `tests/budgets.json` and a check in the smoke test
  that fails when a place goes over. **Proposed budget: 150 draw calls and 120,000 triangles per place** from its spawn
  point. Start by recording today's numbers as each place's ceiling, so nothing gets worse, then lower them as places
  are fixed.
- **A frame-rate readout on the watch** (off by default, in settings): frames per second, worst frame in the last
  second, draw calls. The headless numbers can't tell us what a Quest does; the owner reading these out can.
- **Renderer settings in VR:**
  - turn on fixed foveation through the session's layer (`baseLayer.fixedFoveation = 1`; three r128 has no
    `setFoveation`)
  - offer a quality setting that sets the framebuffer scale (0.8, 1.0, 1.2) before the session starts
- **The camera's extra views:** the eyepiece draws the whole place a third time every frame at 768×576. Draw it every
  second frame when the place is over budget, and make sure the back-screen preview and eyepiece never both draw.

### 4b: the heavy places

One tool fixes most of them: **`mergeStatic(group)` in the core**, generalised from the Birdwatching forest. At the end
of a place's build it bakes every mesh that never moves into a few big meshes:
- plain-colour materials become vertex colours in one mesh
- textured ones are grouped by texture

Anything that moves, hides or is a button is marked and left alone.

- Merge in chunks (for example four per place), so the parts behind you can still be skipped.
- In test mode, keep watching the originals for a few seconds and fail if a merged mesh's position or visibility
  changes: that's a mesh that should have been marked as moving. This is the main trap.
- Order: the study room (one fix, six games), the quest engine (one fix, five quests), recess, football, minigolf,
  haunted, hoops. That's 16 of the 23 places over budget from 7 pieces of work.
- Repeated props (minigolf's flags, carnival ducks, 1,430 meshes in duck shoot): `InstancedMesh`.
- Minigolf, pcbuild and haunted make nearly one material per mesh: share materials by colour through a small cache.

Per-frame costs to check with the readout:
- `new V3` and `new Q4` appear 892 times in game files; the ones inside `update` loops cause pauses on Quest
- boards that redraw their canvas every frame without a change key

**Done when:** as the brief says. Not in scope: moving to a newer three.js (it would help VR drawing, but touches
everything; consider it after these four).

## How this gets done

- **Releases:** every numbered step is its own version with the usual routine. Nothing here needs a "big bang".
- **What needs the owner:**
  - trying step 1.1 on the Quest and on the Claude page (the go/no-go)
  - switching the Hostinger upload from one file to a folder at step 1.5
  - approving the Claude page's room permission at step 2.0, if events turn out better
  - reading the frame-rate numbers off the watch for 4a and 4b
- **Which steps need the stronger model:** 1.1's decision if the Claude page test fails, 2.0–2.4 (the referee,
  hand-over and prediction), and the `mergeStatic` tool. The rest is careful, repetitive work that follows the pattern
  once it's set.
